# Enterprise Platform Observability Standard — iam-authz-enrichment

How this service implements the standard defined and enforced by [platform-gincommon](https://github.com/BCBP-SOLUTIONS-FZC-LLC/platform-gincommon/tree/main/docs/observability) (its `docs/observability/`, shipped with each release). This page covers only what is specific to iam-authz-enrichment. The standard itself, its rules and its governance process are documented there.

## Platform libraries

| Library | Version | Emits here | Wiring |
|---|---|---|---|
| platform-gincommon | v1.6.0 | `platform_grpc_server_*` (the ext_authz `Check` path — this service's real traffic), `platform_http_*` (health/readiness and AsyncAPI routes only), `platform_build_info`; owns the registry | `grpccommon.ObservabilityUnaryInterceptors(grpcCfg)` + `grpccommon.RegisterKnownMethods` in `cmd/server/main.go`; `gincommon.ObservabilityMiddlewares(ginCfg)` in `internal/adapter/inbound/http/router.go`; `/metrics` served by `gincommon.MetricsHandler()` on `METRICS_PORT` (its own listener) |
| platform-events/v2 | v2.0.0 | `platform_messages_*`, `platform_retry_total`, `platform_message_*`, `platform_dependency_request_seconds` (SQS + Glue decode), `platform_event_propagation_seconds`, `platform_library_info{library="platform-events"}` | `events.InitMetrics(events.MetricsIdentityFromLabels(gincommon.MetricsConstLabels()), gincommon.MetricsRegisterer())` |
| platform-pgcommon/v2 | v2.0.0 | nothing: this service has no database (HLD §5.4), so no pool is ever opened and no `platform_db_*` series exist | `pgmetrics.InitWithIdentity(...)` is still called, so a future `postgres.OpenPool` reports with the right identity |

All three register on `gincommon.MetricsRegisterer()`, so one scrape serves every collector. gincommon's Tier 3 constructors refuse to build a collector before gincommon's identity exists, so the order in `cmd/server/main.go` is fixed:

1. `gincommon.InitTracingWithConfig`, with the same identity as below.
2. `gincommon.ObservabilityMiddlewares(ginCfg)`, which fixes the metrics identity.
3. `metrics.New(gincommon.MetricsRegisterer())`, which builds this service's collectors. An error fails startup.
4. `events.InitMetrics`, then `pgmetrics.InitWithIdentity` (`initLibraryMetrics`).
5. `grpccommon.ObservabilityUnaryInterceptors(grpcCfg)`, with the same identity again. gincommon rejects a different second identity with `ErrIdentityMismatch`.

`TestStandard_ProductionRegistrationOrder` (`internal/adapter/outbound/metrics/standard_test.go`) reproduces this order on gincommon's real registerer, records a sample with every production label value, and writes the scrape that `metricslint` and the inventory generator read. The metrics test binary's `TestMain` initialises gincommon with the production service name first.

## Tiers in this service

| Tier | Namespace | Built by | Count |
|---|---|---|---|
| 1 — platform-shared | `platform_*` | The libraries. This service builds none of them itself. | see [inventory](metric-registry.md) |
| 2 — IAM domain-shared | `iam_*` | — | 0. None of the registry's `iam_*` concepts apply to a stateless decision point. |
| 3 — service-specific | `iam_authz_enrichment_*` | `gincommon.NewCounterVec` / `NewCounter` / `NewHistogramVec` in `recorder.go`, which validate the `iam_authz_enrichment_` prefix, the `_total`/`_seconds` suffixes and the prohibited labels, and inject the identity | 12 |

Label **values** stay inside the registry vocabulary:

- `iam_authz_enrichment_decisions_total{decision}` ∈ `allow`, `deny`.
- `iam_authz_enrichment_deny_reason_total{reason}` is the `DenyReason` **lowercased**, because the registry's `reason` pattern is snake_case (`^[a-z][a-z0-9_]{0,63}$`). The values are `deny_unresolvable_subject`, `deny_tenant_read_only`, `deny_mfa_stale`, `deny_tender_acl_insufficient`, `deny_role_insufficient`, `deny_service_unavailable` and `deny_malformed_identity`. The upper-case `DenyReason` on the wire (LLD §9) is unchanged.
- `platform_grpc_server_*{grpc_method}` is limited to the registered services (`Check`, `grpc.health.v1.Health`, reflection outside `prod`) by `grpccommon.RegisterKnownMethods`; anything else is recorded as `unknown`.
- `platform_dependency_request_seconds{outcome}` ∈ `success`, `error`.

No metric carries a high-cardinality label (`tenant_id`, `user_id`, `tender_id`, `event_id`, ...). Those appear only in logs and spans.

## Who counts what (no double counting)

- **Decisions.** `Checker.Check` records `iam_authz_enrichment_decisions_total` exactly once per `Check` call. That includes a request with no verified subject: the gRPC adapter hands it to `Check`, which denies it as `DENY_MALFORMED_IDENTITY` first thing.
- **A deny is not a gRPC error.** `Check` answers a deny inside a successful RPC (`grpc_code="OK"`), so `platform_grpc_server_handled_total{status_class="5xx"}` counts only transport and internal faults. That is what the release gate measures. Denies are on `iam_authz_enrichment_deny_reason_total`.
- **Dead letters** (LLD §16 AE-36). platform-events forwards poison messages to each queue's own RedrivePolicy DLQ (`WithDLQForwarding`) and counts each forward once in `platform_dlq_messages_total{operation="consume"}`. A body that is not an envelope, or a Glue frame that fails to decode, is forwarded on first receipt and also counted in `platform_messages_failed_total{reason="malformed"|"decode_error"}`. A failing message is forwarded on its 5th delivery, after `consumer.DeadLetterHandler` logs it. SQS's own redrive is the backstop when a forward fails. DLQ *depth* is watched by the CloudWatch alarms in `dlq-alarms.tf.example`; `platform_dlq_depth` needs `SQS_QUEUE_DEPTH_INTERVAL`.
- **Duplicates.** Dedup is Valkey `SET NX` on `ae:processed:{event_id}` (LLD AE-6), not platform-events' inbox, so `platform_duplicate_messages_total` is not emitted and no Tier 3 duplicate counter exists.
- **Receive errors.** `platform_dependency_request_seconds_count{dependency="sqs",operation="receive_message",outcome="error"}` has no `queue` label. The per-queue signal is the receive watchdog's own tracker in `cmd/server/receive_watchdog.go`, which restarts the pod and logs the queue.
- **Outbound sibling calls** (I-8, I-14, TAC-4) are timed only by the Tier 3 `iam_authz_enrichment_i8/i12/i14_call_latency_seconds` histograms. They are not on `platform_dependency_request_seconds`, which platform-events records only for SNS/SQS/codec calls.

## Adding a metric

1. Decide the tier with the standard's decision tree. A new `platform_*` or `iam_*` metric is a registry PR to platform-gincommon, never a local definition.
2. Tier 3: add it to `New` in `recorder.go` through the `builder` (`counterVec`, `counter`, `histogram`) as `iam_authz_enrichment_<name>`, with `_total` for a counter or `_seconds` for a histogram. Labels must be snake_case, and no `*_id`, `email` or `ip` labels. gincommon rejects anything else and `New` returns the error naming the metric. Never use `prometheus.New*` or `promauto`.
3. Add the method to the `usecase.Recorder` port and `NoopRecorder` (`internal/usecase/ports.go`).
4. Record a sample for **every** production label value in `exerciseEveryCollector` (`standard_test.go`), so `metricslint check` validates them. The registry check is what caught the upper-case `reason` values.
5. Run `make metrics-inventory` and commit the regenerated [`metric-registry.md`](metric-registry.md); update LLD §11.2 and add any rename to [`migration.md`](migration.md).
6. If it backs an alert, add the alert to `deploy/monitoring/app-alerts.yml` only, run `make prometheusrule`, add a case to `deploy/monitoring/tests/app-alerts.test.yml`, and add an entry to [`runbooks.md`](runbooks.md) (the alert's `runbook` annotation points at it).

## CI enforcement

All in `make metrics-check`, run by `Validate / Quality` (`.github/workflows/validate-quality.yml`) and `make ci`:

| Check | What it enforces |
|---|---|
| `check-metric-naming.sh` (`make metrics-naming`) | No `prometheus.New*`/`promauto` in the metrics package; every collector in `recorder.go` is `iam_authz_enrichment_<snake_case>`, `_total` on counters, `_seconds` on histograms |
| `metrics-registry-lint.sh` (`make metrics-registry-lint`) | No alert queries a `proposed` registry metric unless it carries `metric_status: proposed`. Status comes from the pinned registry, since this service has no local `PlatformRegistry` |
| `metricslint.sh` (`make metrics-lint`) | platform-gincommon's `metricslint check` on `TestStandard_ProductionRegistrationOrder`'s real scrape (registry compliance, label vocabulary, cardinality), with `-allow-proposed-owner platform-gincommon,platform-events,platform-pgcommon`; `metricslint refs deploy docs` (no removed or unregistered names in rule and manifest files); [`metric-registry.md`](metric-registry.md) matches the generator |
| `render-prometheusrule.py --check` (`make prometheusrule-check`) | The Helm PrometheusRule is exactly what `app-alerts.yml` renders to |
| `make rules-test` | `promtool check rules` and the unit tests in `deploy/monitoring/tests/app-alerts.test.yml` (local `promtool`, else the `prom/prometheus` image) |
| `TestStandard_ProductionRegistrationOrder` / `TestNew_AppliesGincommonConstLabels` (`make test-ci`) | Production registration order; no library metric disabled; `version` only on `platform_build_info`; every Tier 3 series passes `obsregistry.Validate` |

`metricslint check -strict` would fail today on the library-owned `proposed` entries; they are allowed through `-allow-proposed-owner`, as in iam-org-membership.

## Items awaiting ratification

Proposed registry entries this service depends on:

- **gRPC server metrics:** `platform_grpc_server_handled_total` backs the release health gate (labelled `metric_status: proposed` in `release.yml`), and `platform_grpc_server_handling_seconds` is the natural end-to-end latency SLI once ratified.
- **platform-events' non-canonical metrics:** `platform_dependency_request_seconds`, `platform_event_propagation_seconds`, `platform_messages_in_flight`, `platform_message_processing_duration_seconds`, `platform_message_timeouts_total` and `platform_queue_depth`. They are owned by platform-events. No live alert queries them.
- **gincommon's HTTP metrics and `platform_build_info`:** owned by platform-gincommon.

The five canonical messaging metrics this service emits (`platform_messages_received_total`, `_processed_total`, `_failed_total`, `platform_retry_total`) are `approved`.

## SLOs

From LLD §11.1, alerted in `app-alerts.yml` (no separate recording-rule file yet):

| SLO | SLI | Target | Alert |
|---|---|---|---|
| Decision latency | p99 of `iam_authz_enrichment_decision_latency_seconds` | 15 ms budget (LLD §11.1); alert at 50 ms (HLD §12.4) | `AuthzEnrichmentDecisionLatencySLOBreach` (5m, SEV-2) |
| Availability | `avg_over_time(up[10m])` across the fleet | 99.9% monthly; alert below 99.5% over 10m | `AuthzEnrichmentAvailabilitySLOBreach` (SEV-1) |
| Cache hit ratio | `rate(..._cache_hits_total) / rate(..._cache_lookups_total)` | ~95% (HLD §8.3); alert below 50% | `AuthzEnrichmentCacheHitRatioLow` |
| Dependency health | `rate(..._stale_if_error_served_total)`, `..._deny_reason_total{reason="deny_service_unavailable"}` | 0 | `AuthzEnrichmentStaleIfErrorServing` (page), `AuthzEnrichmentServiceUnavailableSpike` |
| Event delivery | `increase(platform_dlq_messages_total{operation="consume"}[15m])`; `platform_messages_failed_total / platform_messages_received_total` per queue | 0 forwards; < 50% failing | `AuthzEnrichmentDLQForwards`, `AuthzEnrichmentEventFailureRateHigh` |

Every metric alert aggregates `by (domain, service, environment)`, so it fires per environment and carries the identity; the `up`-based alerts select on the scrape job and set `domain`/`service` as static labels. Every alert has a `runbook` annotation pointing at its entry in [`runbooks.md`](runbooks.md).

There are no multi-window burn-rate rules yet. The availability SLI is scrape health, not a request-success ratio. Because a deny is a successful RPC, the request-level equivalent would be the `platform_grpc_server_handled_total` 5xx share plus `deny_service_unavailable`.

## HPA

`deploy/monitoring/prometheus-adapter-rule.yaml` exposes `iam_authz_enrichment_decisions_per_second` (from `iam_authz_enrichment_decisions_total`) as the per-pod HPA input (`autoscaling.targetDecisionsPerSecondPerReplica`, default 500). CPU and memory remain the fallback when the adapter rule is not installed.
