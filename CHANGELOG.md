### Added

- **tenant-authz-q expanded from 2 → 8 event types** (AE-RP-GAP-002..006, CD-37, LLD §16 AE-38): `TenantSettingChanged` (CD-37 — tenant owner changed a setting, e.g. `residency_mode`; triggers `ae:tenant` eviction), `TenantSuspended` (RP-14 operator/billing-lapse suspension), `TenantReactivated` (operator-sourced, RP-10 — distinct from the billing-sourced `TenantReactivated` on `billing-authz-q`), `TenantOffboarded` (full realm deletion), `TrialExpired` (RP-C1 CronJob, clears `read_only` gate), and `TrialReactivated` (trial extension). - `test/fixtures.FakeCache.EvictTenantErr` — write-side error injection for `EvictTenantContext`, completing the full error-coverage parity with the other `Evict*Err` fields.

- Tests: `cmd/server` unit tests for `loadServerTLS` (TLS, mTLS and every failure), `initLibraryMetrics` (fails before gincommon's identity, succeeds after) and `startConsumers` (idle in dev; a queue without a RedrivePolicy reaches the fatal channel); e2e startup tests on the real binary — fail-fast exits for a dev-default sibling URL, a blank queue URL outside dev, a malformed `rediss://` URL, a non-positive `GRPC_REQUEST_TIMEOUT`, missing TLS files, an occupied gRPC port and a queue without a RedrivePolicy, plus SIGTERM exiting 0. `make cover-all` merges unit coverage with an e2e run of a coverage-instrumented binary: whole module 96.9%, `cmd/server` 82.3% (was 16% from unit tests alone).

### Changed

- **Sibling timeouts re-baselined (LLD §16 AE-37):** `ORG_MEMBERSHIP_TIMEOUT` 10ms → 40ms and `TENDER_ACL_TIMEOUT` 20ms → 30ms — the old values were at or below the siblings' own p99 targets, so healthy calls timed out. New `GRPC_REQUEST_TIMEOUT` (250ms) caps each `Check` server-side; the README Envoy sketch uses a 250ms ext_authz timeout and sets `failure_mode_allow: false` explicitly.
- **Helm production hardening:** no CPU limit (CFS throttling vs. the 15ms p99 budget) with a 250m request and `GOMEMLIMIT=230MiB`; topology spread across zones (hard) and nodes (best effort) replaces hard one-pod-per-node anti-affinity, which needed ≥5 nodes and blocked HPA scale-out; rollouts surge (`maxSurge: 1`, `maxUnavailable: 0`); `LOG_SAMPLING=true`. The chart refuses to render `APP_ENV=prod` with plaintext gRPC unless `grpcTLS.enabled` or `grpcTLS.meshProvidesMTLS` is set (release.yml reads the latter from the `MESH_PROVIDES_MTLS` repo variable).
- `docs/runbook.md` gains a go-live checklist (infrastructure, dependency tracking, and the risk acceptances that need sign-off).

- **Helm env aligned with iam-org-membership and the shared libraries.** Added: `APP_NAME`, `LOG_LEVEL`, `LOG_SAMPLING`, `OTEL_TRACES_SAMPLER_RATIO`, `OTEL_PROPAGATOR_BAGGAGE`, `OTEL_TRACES_IGNORE_REMOTE_PARENT_SAMPLED`, `SQS_HANDLER_TIMEOUT` (20s), `SQS_DRAIN_TIMEOUT` (30s, the library default the shutdown budget assumes), `SQS_QUEUE_DEPTH_INTERVAL` (60s), the five `*_AUTHZ_QUEUE_CONCURRENCY` values and `DOCS_ENABLED`. `OTEL_EXPORTER_OTLP_ENDPOINT` now points at the cluster collector (`otel-collector.observability.svc.cluster.local:4317`, already allowed by the NetworkPolicy) instead of falling back to `localhost:4317`. The IRSA policy adds `sqs:GetQueueAttributes` on the five `-dlq` queues for DLQ-depth sampling. `.env-example` and `docker-compose.yml` gain the same shared-library settings (local runs export no spans: `OTEL_EXPORTER_OTLP_ENDPOINT=none`).

- **Poison messages are forwarded to the queue's DLQ instead of being deleted** (LLD §16 AE-36). Consumers wire platform-events' `WithDLQForwarding` (`consumer.NewDLQPublisher`): a malformed body or failed Glue decode goes to the queue's RedrivePolicy DLQ on first receipt (previously deleted with no DLQ copy), and a failing message on its 5th delivery, after `DeadLetterHandler` logs it. SQS's redrive stays the backstop. **Deployment impact:** the IRSA policy needs `sqs:GetQueueUrl` and `sqs:SendMessage` on the five `-dlq` queues (`deploy/iam/policy.json`), and a consumer now refuses to start on a queue without a RedrivePolicy (the pod restarts).
- **Requests with no verified subject are now counted.** They are denied as `DENY_MALFORMED_IDENTITY` inside `Checker.Check` rather than in the gRPC adapter, so they appear in `iam_authz_enrichment_decisions_total` / `deny_reason_total` and the decision-latency histogram.
- **`ENVIRONMENT` is read when `APP_ENV` is unset** (`config.ResolveAppEnv`: trimmed, lowercased, default `dev`), the precedence the platform libraries already use.
- **Alert rules** aggregate `by (domain, service, environment)` and carry a `runbook` annotation pointing at `docs/observability/runbooks.md`. New alerts: `AuthzEnrichmentDLQForwards` and `AuthzEnrichmentEventFailureRateHigh`. `deploy/helm/templates/prometheusrule.yaml` is now generated from `deploy/monitoring/app-alerts.yml` (`make prometheusrule`).
- **`platform-gincommon` v1.4.0 → v1.6.0, and shared-library APIs used in place of local copies (parity with iam-org-membership).** Glue decoding uses platform-events' `events.GlueDecodeCodec` (local `consumer.GlueDecoder` removed; it now also rejects a non-JSON payload with a clear error). Tracing starts with `gincommon.InitTracingWithConfig` using the same identity as the metrics config; spans and propagation go through `gincommon.NewTracer` / `NewSpanTracer` / `InjectTraceContext` (local `postgres.NewOTelTracer` and `propagateTraceparent` removed). `/metrics` is served by `gincommon.MetricsHandler`. `grpccommon.RegisterKnownMethods` bounds the `grpc_method` label. Business metrics are built through gincommon's registry-validated `NewCounterVec` / `NewCounter` / `NewHistogramVec`; `metrics.New` now returns an error that fails startup instead of panicking.
- **`iam_authz_enrichment_deny_reason_total{reason}` label values are lowercased** (`DENY_SERVICE_UNAVAILABLE` → `deny_service_unavailable`) to satisfy the Platform Observability Registry's snake_case `reason` vocabulary. This was found by the new registry validation. Alert rules (`deploy/monitoring/app-alerts.yml`, the Helm PrometheusRule) are updated. `DenyReason` values on the wire are unchanged.
- **Helm defaults for the two synchronous siblings now point at their real in-cluster Services**
  (IAM convention: namespace `iam`, Service named after the repo, port 8080):
  `ORG_MEMBERSHIP_BASE_URL=http://iam-org-membership.iam.svc.cluster.local:8080` and
  `TENDER_ACL_BASE_URL=http://iam-tender-acl.iam.svc.cluster.local:8080` (both were `""`, which fell
  back to the localhost dev defaults and made `config.Load` refuse to start outside dev).
- **NetworkPolicy egress to both siblings** — new `networkPolicy.upstreamEgress` renders one rule per
  service, restricted to that service's pods in namespace `iam` on 8080
  (`app.kubernetes.io/name: iam-org-membership` / `tender-acl`). Previously neither had an egress rule
  and every I-8/I-14/TAC-4 call would have been dropped by the default-deny policy unless an operator
  added `additionalEgressRules`. iam-tender-acl must list this service's pods
  (`app.kubernetes.io/name: iam-authz-enrichment`) in its `networkPolicy.internalCallerPodSelectors`
  (its README "Onboarding a TAC-4 caller").
- **Migrated to the platform libraries' Enterprise Platform Observability Standard metrics contract (breaking for dashboards/alerts; nothing deployed yet).** `gincommon.Config` / `grpccommon.Config` set `Domain: "iam"` and `Environment: APP_ENV` (`OBSERVABILITY_DOMAIN=iam` also added to Helm values, `docker-compose.yml` and `.env-example`). platform-events and platform-pgcommon are initialised with `events.InitMetrics` / `pgmetrics.InitWithIdentity` from `gincommon.MetricsConstLabels()` on `gincommon.MetricsRegisterer()`; registration warnings are logged and an invalid identity fails startup. Every series now carries `{domain, service, environment}`; `version` is only on `platform_build_info`. The service's own metrics are renamed `authz_*` → `iam_authz_enrichment_*` (Tier 3 prefix; e.g. `iam_authz_enrichment_decisions_total`), with the alerts, PrometheusRule, prometheus-adapter rule and HPA metric (`iam_authz_enrichment_decisions_per_second`) updated. The release deploy gate queries `platform_grpc_server_handled_total{domain="iam",service="iam-authz-enrichment"}` (registry status: proposed).
- `APP_ENV` vocabulary: Helm `values.yaml` `APP_ENV` is `prod` (was `production`, which gincommon now rejects). The production checks in `cmd/server` (gRPC reflection) and the AsyncAPI `DocsConfig` gate compare against `prod`.
- `cmd/server/receive_watchdog.go` no longer reads a Prometheus metric: each consumer gets its own SQS client decorator that counts its `ReceiveMessage` errors and successes, and the watchdog fires after 6 consecutive 30s polls with errors and no successful receive. platform-events' per-queue receive-error counter it used to read was removed; the successor has no `queue` label and is fail-soft. Successes now reset the streak too, so a flaky-but-working queue can no longer trip it.
- Local-dev SQS emulation migrated from LocalStack to floci (`docker-compose.yml`'s `floci`/new `floci-ui` services, new `scripts/init-floci.sh`) — same open-source, always-free LocalStack-compatible emulator `iam-org-membership`/`iam-delegation` already use. CI is unaffected: `scripts/init-localstack.sh` and the bare `localstack` service containers in `validate-test.yml` are unchanged.
- `internal/usecase/check.go`'s `resolveContext` now runs its two Valkey reads (`GetMembershipContext`/`GetTenantContext`) concurrently instead of sequentially — at the 10ms default `VALKEY_READ_TIMEOUT`, two sequential reads could alone approach the 15ms p99 decision budget on a slow-but-not-erroring Valkey.
- Shutdown-phase timeouts rebalanced to actually fit `terminationGracePeriodSeconds` (60s): gRPC `GracefulStop` capped at 10s (was unbounded, see Fixed below) and the shared HTTP/metrics `Shutdown()` timeout reduced from 30s to 10s (neither server holds long-lived connections) — new worst case 10+10+35=55s, a 5s margin, versus a pre-fix worst case that could exceed the grace period even before accounting for the unbounded `GracefulStop`.
- `RestrictedTenderSet`/`RealmMap` now cache negative ("not restricted" / "no such realm") results in L1 with a TTL, instead of hitting Valkey on every `Check()` for a tender/issuer that has never resolved.
- `/metrics` moved off `APP_PORT` to its own dedicated port (`METRICS_PORT`, default 9090).
- `deploy/helm/values.yaml` replica/HPA range corrected to 5–20 to match the LLD's design commitment.
- SQS consumer shutdown parallelized (`sync.WaitGroup`) instead of sequential, bounding worst-case shutdown time.
- `release.yml`'s `deploy-gate` uses a gRPC-specific health query and only runs when `DEPLOY_GATE_ENABLED=true` (default skipped — no cluster provisioned yet).

### Fixed

- **`make vuln-check` / Trivy failed on 9 reachable standard-library vulnerabilities** (GO-2026-6603/6605/6607/6608/6610/6611/6612/6613/6617 in `net/http`, `crypto/tls`, `mime/multipart`). Bumped `go.mod`'s `go` directive 1.26.6 → 1.26.9 and `golang.org/x/net` v0.59.0 → v0.60.0; re-pinned the Dockerfile's `golang:1.26.9-alpine` builder digest via `make pin-base-images`.
- **A fatal shutdown exited 0.** When a background component failed (a dead gRPC/HTTP/metrics server, a consumer that cannot start — e.g. a queue without a RedrivePolicy — or the receive watchdog), `cmd/server` shut down gracefully and then returned nil, so the pod showed "Completed" instead of an error and crash-loops were invisible to restart-count alerting. It now exits non-zero with the cause; a SIGTERM shutdown still exits 0. Found by the new startup e2e tests.
- **A clean SIGTERM shutdown exited 1 on Linux.** `run()` returned the logger flush error from `grpccommon.Shutdown`, and zap's `Sync` fails with `EINVAL` when stderr is a pipe — true under every container runtime — so every rolling restart looked like a failure. A flush error is now only logged (as iam-org-membership does) and never sets the exit code. Found by `TestShutdown_SIGTERM_ExitsZero` in CI.

- **Event processing shared the request path's 10ms Valkey timeouts.** A single slow Valkey round trip failed an eviction or a `TenderRestricted` write, and its retry then waited a full 30s visibility timeout (found as the e2e tender-ACL test's intermittent failure). Event processing now uses its own Valkey client (`VALKEY_EVENT_TIMEOUT`, 500ms) — the invalidator, the `ae:processed` ledger and the `ae:restricted`/`ae:realm` writes — while request-path reads keep the 10ms timeouts.
- e2e suite made deterministic: consecutive runs shared queues, and a stopped binary's still-open 20s long poll on the emulator could swallow the next run's event for a 30s visibility timeout. The harness now runs the binary with `SQS_WAIT_SECONDS=1` and `SQS_VISIBILITY_TIMEOUT=5s` (8/8 back-to-back runs pass; previously ~4 of 5 failed).

- **Healthy requests denied when another request was cancelled.** Concurrent cache misses for the same user share one I-8 call (singleflight), which ran under the first caller's context; when Envoy's deadline cancelled that request, every request waiting on it failed too and was denied `DENY_SERVICE_UNAVAILABLE`. The shared call now uses `context.WithoutCancel`, bounded by `ORG_MEMBERSHIP_TIMEOUT` (regression test included).
- **`make vuln-check` scanned only `./internal/...`** and so missed GO-2026-6443, a grpc server panic reachable from `cmd/server`. It now scans `./...` and fails on any reachable vulnerability not listed, unexpired, in `.github/govulncheck-allow.txt` (GO-2026-6443 is accepted until 2026-11-15 — no released grpc fix yet; ingress is limited to Envoy).
- A `VALKEY_URL` that looks like a URL but does not parse now fails startup instead of silently falling back to a plain address.

- `SQS_QUEUE_DEPTH_INTERVAL` had no effect: each consumer's SQS client is wrapped by the receive watchdog, and the wrapper hid `GetQueueAttributes`, so platform-events skipped `platform_queue_depth` / `platform_dlq_depth` sampling. The wrapper now forwards it.
- A `PG_USER/PG_DBNAME ... required to build a DSN` warning was logged on every startup although this service has no database; it is now dropped when no database env is set at all (a partial `PG_*` config still warns).

- **Glue-encoded inbound events were undecodable (LLD AE-35).** The consumers used `events.NoopCodec`, so any event from a producer with its Glue registry configured (every IAM sibling) reached the handlers with its 18-byte Glue header, failed `json.Unmarshal`, and dead-lettered after 5 attempts with its cache eviction never applied — stale authorization until TTL, and indefinitely for `TenderRestricted`. The new decode-only `consumer.GlueDecoder` strips the header; plain-JSON envelopes are unaffected.
- **`grpcServer.GracefulStop()` had no timeout.** A wedged Envoy connection or a `Check()` call stuck on a hanging downstream call would stall every later shutdown step (HTTP shutdown, SQS consumer drain, `cache.Close()`) until Kubernetes' `terminationGracePeriodSeconds` expired and SIGKILLed the pod, skipping the graceful consumer drain entirely. Fixed by running `GracefulStop()` in its own goroutine with a 10s cap, falling back to a hard `Stop()`. Found by a fresh production-readiness code audit, not a reported incident.
- **A handler panic in a SQS consumer left its message permanently marked "processed."** `processedHandler` marked a message processed before running its handler, and only evicted that marker on a *returned* error — a panic was recovered by `platform-events`' own top-level recovery, outside this app's eviction path, so any redelivery was silently skipped forever (or until the 7-day TTL). For `tender-authz-q`'s `TenderRestricted`, the blast radius was unbounded: `ae:restricted` has no TTL by design, so a panic there would have permanently disabled the tender-ACL overlay for that tender with no automatic recovery. No live trigger existed (every handler's JSON decode is already error-checked), so this was a defense-in-depth gap, not an active incident. Fixed with a `recover()` that runs the same cleanup before re-panicking.
- `internal/config/config.go` accepted a zero or negative value for `GRPC_MAX_CONCURRENT_STREAMS`, both gRPC message-size limits, and all five `*_AUTHZ_QUEUE_CONCURRENCY` vars without complaint — a gRPC server silently configured with zero concurrent streams, or a consumer built with negative concurrency, instead of failing fast at startup the way every other class of operator typo in this file already does. Fixed with a new `envPositiveInt` validator; `GRPC_MAX_CONCURRENT_STREAMS` additionally gets an explicit `uint32`-range check before its narrowing conversion.
- Dependabot opened one PR per individual dependency bump across all three ecosystems (gomod/docker/github-actions), each running this repo's full required pipeline (real Valkey/LocalStack integration tests, lint, docker build, Trivy, smoke test — six status checks). `github/codeql-action` alone was bumped 4 separate times in under a month, each a full pipeline run for an unreviewed patch version. Fixed by grouping all minor/patch updates into one PR per ecosystem per week (`.github/dependabot.yml`'s new `groups:` blocks); major bumps stay ungrouped and individually reviewed, since those can be breaking or (for the golang Docker base image specifically) require a coordinated `go.mod` change — see the entry below on that exact failure mode.
- Dockerfile's pinned builder image (`golang:1.26.5-alpine`) was one patch version behind `go.mod`'s `go 1.26.6` requirement, so `docker build` failed immediately at `go mod download` with `go: go.mod requires go >= 1.26.6 (running go 1.26.5; GOTOOLCHAIN=local)` — every image build was broken, not just a local dev inconvenience. Fixed by re-pinning to `golang:1.26.6-alpine` (fresh digest). `make pin-base-images` now derives the golang image tag from `go.mod`'s own `go` directive instead of a second hardcoded version string in the `Makefile`, so a future `go.mod` bump and this pin can't silently drift apart again the same way.
- `/asyncapi` HTML viewer rendered `�` instead of the description — byte-level string truncation split multi-byte UTF-8 characters. Fixed with a rune-boundary-safe `truncateRunes` helper.
- `api/asyncapi.yaml`'s producer-summary table incorrectly listed the same combined producer for `billing-authz-q` and `tenant-authz-q`; corrected to each queue's actual distinct producer.
- A few CI script bugs: a hadolint false-positive on `ENV GOPRIVATE`, a SIGPIPE in `extract-release-notes.sh`, and `export-image-provenance.sh` reading provenance attestations with the wrong tool.
- Gin never switched out of debug mode outside `APP_ENV=dev` — unlike `iam-org-membership`/`iam-user-profile`, nothing in `cmd/server/main.go` called `gin.SetMode(gin.ReleaseMode)`, so every deployment (including production) ran Gin in debug mode: per-route registration spam on every startup and Gin's own "switch to release mode" warning in the logs permanently. Found by actually running the built binary end-to-end (grpcurl/curl walkthroughs, both `APP_ENV=dev` and `=production`) rather than by static analysis. Fixed by adding the same `if cfg.AppEnv != "dev" { gin.SetMode(gin.ReleaseMode) }` guard the sibling services already use.
- **I-8 wire-format mismatch**: `internal/adapter/outbound/orgmembership/client.go`'s `departmentDTO.Level` was tagged `json:"level"`, but Org & Membership's real I-8 response uses `"role_level"` for the same field (verified against that service's actual `GetMemberships` handler and its own LLD's documented example). Every department's level silently decoded as `""` on every real request, corrupting the `x-departments` header (`department_id:` instead of `department_id:level`) and permanently failing any `required_department_level` policy gate — fail-closed, not an authorization bypass, but a live functional/interoperability defect. This service's own contract test and README's mock-Org-&-Membership walkthrough had independently encoded the same wrong field name, which is why nothing caught it; both corrected alongside the fix. Verified end-to-end against a running binary with a corrected mock.
- `api/asyncapi.yaml`, `README.md`, and the LLD stated no published `asyncapi.yaml` was available to verify Realm Provisioner's `TenantConverted`/`TenantRealmReady` event schemas against — stale: the spec is present in this workspace and, checked field-for-field, matches this service's decoding exactly (`realm: {type: string}` both sides). `producer-lifecycle-status` upgraded `unknown` → `stable` for both messages; documentation-only, no behavior change (LLD §16 AE-27).
- **gRPC/HTTP/metrics server death after startup was invisible to both health probes and the pod-restart path.** `deploy/helm/values.yaml`'s liveness/readiness probes are `httpGet` against the HTTP server only — there is no `grpc:` probe against the native health service on the gRPC port. `main.go`'s three server goroutines only logged an unexpected `Serve`/`ListenAndServe` exit; nothing fed it to the existing `consumerFatal` restart channel. An unexpected death of `grpcServer.Serve` — the entire ext_authz decision path, 100% of Envoy's traffic — would leave `/healthz`/`/readyz` reporting healthy forever with no pod restart: a total, silent outage. Fixed by routing all three servers' non-graceful exits into the same shared fatal-error channel (renamed `fatalErr`) via a `reportFatal` helper, reusing the identical restart path a consumer death or the receive-error watchdog already trigger (LLD §16 AE-28).
- **Critical: every I-8/I-14 call to Org & Membership was missing required internal-service-identity headers.** Org & Membership's `/internal/*` routes (I-8 `GetMemberships`, I-14 `GetMFAFreshness`) are gated by an application-level `RequireSystemRole()` check requiring `x-user-id: iam-system` / `x-tenant-id: <tenant>` / `x-tenant-roles: iam-system` — the same convention that service's own five outbound clients to sibling internal APIs all use. This client sent none of them. **Impact was total, not partial**: every real (non-mocked) call would 403 before reaching the handler, so the core cache-miss-rebuild path could never succeed against a real Org & Membership instance — undetected because every mock used so far (including this project's own tests and README walkthrough) doesn't reimplement the callee's auth middleware, so it accepted requests regardless of headers sent. Fails closed (degrades/denies via the existing §7 failure matrix), never a bypass. Fixed by setting all three headers on `GetMemberships`/`GetMFAFreshness`; `GetTenderACL` (TAC-4, mesh-only/no-RBAC on `iam-tender-acl`'s side) deliberately continues to send none, with a dedicated regression test guarding the distinction. Verified against a running binary and a hand-built mock that reimplements Org & Membership's exact `RequireSystemRole` check (403 without the fix, 200 with it).

### Removed

- Helm `env.SQS_MAX_RECEIVE_COUNT` and `env.OTEL_SERVICE_NAME`: the first was overridden in code (the consumer pins its threshold to 4) and only misled; the second is redundant because `APP_NAME` is passed to gincommon explicitly. The Postgres / outbox / SNS variables are removed from `.env-example` — this service has no database and publishes nothing; `cmd/server` still warns if any is set.
- `active_delegations[]` / `domain.Delegation` — dropped entirely; delegation state moved to its own service (`iam-delegation`, ADR-0008).
